## 1. UA3F（校园网防检测）

配置：`/etc/config/ua3f` — TPROXY / 1080 / UA=Linux Chrome 141 / `l3_rewrite_ttl=1（65）`、`ipid=1`、`tcpts=1`、`tcpwin=1`、`block_quic=1`、`log_level=WARN`。
服务：`/etc/init.d/ua3f`（procd，START=99，已 enable）。

**结构**：两张 nft 表都由 UA3F 二进制在启动时生成，**没有配置项、也不能手工改后永久保留**。

- `inet UA3F`（priority 20）：tproxy 拦截，已 return 127/8、LAN 段、SKIP_IPSET、22/51080/51090。
- `inet UA3F_HELPER`：
  - `TTL`：WAN 出口把 TTL 改成 65（上游 360 再 -1，校园侧看到 64）
  - `HELPER_QUEUE`：TCP SYN 与 `ip id != 0` 的包排队到用户态 10301，改写 IPID / TCP 时间戳 / 窗口
  - `BLOCK_QUIC`：drop udp/443

### 1.1 已打的两个补丁（2026-10-28，用户批准）

```
HELPER_QUEUE:  oifname "lo" return          # 回环不排队（修 8KB 卡死）
TTL:           oifname != "eth0" return     # TTL 只改写 WAN
```

落地方式（因为 UA3F 每次启动重建链，手工规则必丢）：
- `/usr/bin/ua3f-nftfix`：幂等检查+插入两条规则
- `/etc/init.d/ua3f-nftfix`：procd，START=99，已 enable，每 30s 补齐一次
- `/usr/bin/ua3f-nftfix-watch`：上面服务跑的死循环脚本

### 1.2 坑位清单（重要）

1. **TTL 规则写死了 `eth0`**。以后 WAN 改成 PPPoE（pppoe-wan）或换网卡名，TTL 会**静默不再改写**——网络照常通，但伪装失效。必须同步改 `/usr/bin/ua3f-nftfix` 里的接口名，然后 `sh /usr/bin/ua3f-nftfix`。
2. **手工 `nft insert` 的规则在 UA3F 重启/崩溃后消失**。不要直接加，改脚本。
3. **HELPER_QUEUE 曾经没有排除回环**，导致路由器本机到 127.0.0.1 的 TCP 超过 8KB 就卡死（uhttpd 下载只拿到 8192B）。所以**不要从路由器本机测节点/下载速度**，会得出"所有节点卡在 ~10KB"的错误结论；要从 LAN 里的电脑测。
4. **必须保持 flow offloading 关闭**：`uci get firewall.@defaults[0].flow_offloading` 应为 `0`，否则 UA3F 的 TTL/IPID 改写会失效。
5. UA3F 停用 = TTL/UA/QUIC 全套伪装消失（网络仍可用，但校园侧可识别）。

### 1.3 验证命令

```sh
# 1) 两条补丁在不在（TTL 第一行应为 oifname != "eth0" return）
nft list chain inet UA3F_HELPER TTL | head -5
nft list chain inet UA3F_HELPER HELPER_QUEUE | head -5

# 2) 回环自检：应返回 228821，且 <0.1s；若只有 8192 说明补丁丢了
curl -k -s -m 15 -o /dev/null -w '%{size_download} %{time_total}\n' https://127.0.0.1/cups.pdf

# 3) WAN 出口伪装：应看到 ttl 65、id 0
tcpdump -i eth0 -nn -v -c 4 'tcp and src host 192.168.20.3 and dst port 443'
```

### 1.4 回滚

```sh
/etc/init.d/ua3f-nftfix disable && /etc/init.d/ua3f-nftfix stop
rm /usr/bin/ua3f-nftfix /usr/bin/ua3f-nftfix-watch /etc/init.d/ua3f-nftfix
nft -a list chain inet UA3F_HELPER HELPER_QUEUE   # 取 handle 后 nft delete rule ...
# 整份改动前规则：/root/nft-ruleset.bak-20261028-before-loopfix
```

### 3.3 局域网文件传输（替代已删除的 Flashdrop / PairDrop）

- 两者都 `S98` 随系统自启；端口在 LAN zone（input ACCEPT），不需要改防火墙
- 注意：同时起两个服务做过端口测试，误留的手工进程会占住 8080 让 procd 报 `address already in use`——排查看 `logread | grep file-transfer`
- **共享桌面必须 HTTPS**：`getDisplayMedia` 只在安全上下文可用，纯 http+IP 会被浏览器挡。ftg 自身没有 TLS 参数，所以加了一层 nginx（Docker，`--network host`）：
  - 证书：`/mnt/sata1-4/tls/ftg.crt|ftg.key`，自签 10 年，SAN `IP:192.168.10.1, IP:127.0.0.1, DNS:localhost`

  - 容器：`ftg-tls`（`nginx:alpine`，`--restart unless-stopped`）；入口 `https://192.168.10.1:8443`，导航页「文件快传 P2P」已指向它（siteMonitor 仍用 http 8080，因为 Homepage 不认自签证书）
  - 前端 JS 逻辑：`https:` 协议时自动用 `wss://当前host`，所以代理后信令不用改代码
  - 首次访问要点「高级 → 继续前往」；Chrome 越过该页后 `isSecureContext` 为 true，共享桌面可用
  - 无警告的替代：`ssh -L 8080:192.168.10.1:8080 root@192.168.10.1` 后开 `http://localhost:8080`（localhost 天生是安全上下文）
  - 回滚：`docker rm -f ftg-tls`（ftg 本体和 8080 不受影响）

**P2P 为什么一直不可用（2026-10-29 实测，已解决）**

- 症状：页面状态写「P2P不可用，已自动切换到服务器中继传输」，共享桌面直接提示「中继模式不支持桌面视频流」；文字/文件能传但走服务器中转
- 根因（两段，第二段才是关键）：
  1. Chrome 的 host candidate 被 mDNS 伪装成 `<uuid>.local`，而这套 LAN 上 **mDNS 无响应**（向 224.0.0.251 连发 6 次，0 应答）；公网 STUN 只会给出校园 NAT 出口地址（`223.154.198.x`），LAN 内发夹失败
  2. 加了局域网 STUN 后手机能拿到 `srflx 192.168.10.109:端口`，**但这条路径只通一半**：手机发往 PC 的检查包全到（实测 114/115），PC 回的 STUN **响应包全丢**（实测 230 发出、0 到达），手机侧 ICE 永远停在 `checking`，10 秒后代码兜底切中继。两台手机（OnePlus PLM110、小米 MI 5）现象完全一致，所以不是手机问题
- 判定方法（可复现）：手机建房间、PC 加入 → **P2P 成功**（手机从 PC 的包里 reflexive 学到 `prflx`，绕开 mDNS）；PC 建房间、手机加入 → **必中继**。差别只在 PC 侧 host candidate 是 mDNS 还是真实 IP
- 修复：让 PC 的 Chrome 对本机这两个地址暴露真实内网 IP（不再用 `.local`）。已验证：改完后 PC 建房间也能直连，手机端稳定收到 1920×1080 桌面视频
  - 已落地的方案（Chrome 企业策略，HKLM，需要管理员）：`HKLM\SOFTWARE\Policies\Google\Chrome\WebRtcLocalIpsAllowedUrls`，字符串值 `1 = https://192.168.10.1:8443`、`2 = http://192.168.10.1:8080`。改完**重启 Chrome**，`chrome://policy` 里能看到 `WebRtcLocalIpsAllowedUrls`
  - 回滚：删掉 `HKLM\SOFTWARE\Policies\Google\Chrome\WebRtcLocalIpsAllowedUrls` 整个键，重启 Chrome
  - 免管理员替代：Chrome 快捷方式加启动参数 `--disable-features=WebRtcHideLocalIpsWithMdns`（效果相同，但只对从这个快捷方式启动的实例生效）
  - 注意策略要覆盖实际访问的 origin；共享桌面走 `https://192.168.10.1:8443`，所以 8443 这条必须有
- 路由器侧仍保留的辅助设施（对手机侧 / 8080 入口有用，不是根因）：
  - `coturn` 局域网 STUN（opkg 装，`/etc/turnserver.conf` 里 `stun-only` + `no-auth` + 只绑 `listening-ip=192.168.10.1`，不开 TURN 分配、不对外），`/etc/init.d/coturn` START=97，RSS ≈ 8 MB
  - `ftg-tls` 的 nginx 用 `sub_filter` 在 `</head>` 前插脚本，把 `stun:192.168.10.1:3478` 写进前端 `localStorage["webrtc-ice-servers-config-090901"]`；**必须同时 `proxy_set_header Accept-Encoding "";`**，否则上游压缩后 `sub_filter` 匹配不到。只在 8443 生效，直连 8080 不带注入（前端「添加ICE服务器」也可手工加）
  - 回滚：`/etc/init.d/coturn disable; /etc/init.d/coturn stop; opkg remove coturn`；nginx 删掉两行 `sub_filter` 后 `docker restart ftg-tls`
- **使用前提（踩过的坑）**：
  - 手机必须留在 `HMCL26_5G`/`HMCL26_2.4G`。实测它自动漫游到校园网 `Xiaoyuanwang`（10.200.x/16）后，连 `192.168.10.1` 都 ping 不通，P2P 和中继一起失效
  - 观看时手机别熄屏：息屏后 Chrome 被冻结，`chrome_devtools_remote` 停响应、WebRTC 直接断
  - 手机是纯观看端：Android Chrome 没有 `getDisplayMedia`，页面会显示「移动端不支持屏幕分享」

## 5. 负载与排查

### 5.1 先分清三类"卡"

```sh
vmstat 1 3          # us/sy 高 = 真吃 CPU；wa 高 = 等磁盘/IO；id 高但 load 高 = D 状态阻塞
cat /proc/loadavg   # 最后两列是 运行中/总进程 与 最近 pid
top -b -n2 -d2 | head -16          # 注意 head 才是 CPU 最高的，tail 是最低的
for d in /proc/[0-9]*; do s=$(awk '{print $3}' $d/stat 2>/dev/null); [ "$s" = D ] && echo "${d##*/} $(cat $d/comm)"; done
```

**load 高 ≠ CPU 占满。** 2026-10-28 18:47 实测：load 5.8~7.1，但 CPU `9% usr / 9% sys / 40% idle / 40% io`；D 状态集中在 `flush-8:0`、`jbd2/sda4-8`、`postgres`、`parted`、`lsblk` —— 是 sda 这块盘 I/O 阻塞，不是 CPU 算力不够。先查盘再谈扩容。

```sh
# 公网 DoH 能拿到真实记录（www → 220.170.193.14），直连公网 IP + SNI 返回 200
curl -s 'https://dns.alidns.com/resolve?name=www.hnsyu.edu.cn&type=A'
curl -s -o /dev/null -w '%{http_code}\n' --resolve www.hnsyu.edu.cn:443:220.170.193.14 https://www.hnsyu.edu.cn/
```

两个独立病因，缺一不可：

1. **校园 DNS 对校内用户返回内网地址**：www/oa → `172.18.2.253`，jwgl → `172.18.2.45`，authserver → `172.18.18.47`。dnsmasq `rebind_protection=1` 丢弃私有地址应答，客户端拿到 NXDOMAIN（`logread | grep rebind` 有 `possible DNS-rebind attack detected`）。原来 `rebind_domain` 只有 `hnsyu.net`，不含 `hnsyu.edu.cn`。
2. **这些 172.18.x 撞上 Docker 的 `172.18.0.0/16`**：LAN 转发查 main 表命中 docker 网桥，包出不了 eth0。注意 WAN 配了 `ip4table='default'`（表 253），uci 里的 `@route` 段**不会出现在 main 表**，10-28 加的那两条静态路由一直是无效配置。

修法：

```sh
# 1) 防重绑定白名单
uci add_list dhcp.@dnsmasq[0].rebind_domain='hnsyu.edu.cn'
uci commit dhcp

# 2) 按网段加进 main 表（不是 /32，学校换机器只要还在同网段就不用改）
for net in 172.18.2.0/24 172.18.18.0/24 172.18.19.0/24; do
  ip route replace $net via 192.168.20.1 dev eth0
done

# 3) 持久化：wan 每次 up 后补回（netifd 会在 ifdown/续租时清掉运行期路由）
#    /etc/hotplug.d/iface/99-campus-routes
```

热插拔脚本内容：

```sh
#!/bin/sh
[ "$ACTION" = "ifup" ] && [ "$INTERFACE" = "wan" ] || exit 0
gw=$(ip route show table 253 | awk '/^default/{print $3; exit}')
[ -n "$gw" ] || gw=192.168.20.1
for net in 172.18.2.0/24 172.18.18.0/24 172.18.19.0/24; do
	ip route replace "$net" via "$gw" dev eth0
done
```

- 验证：PC 上 `nslookup` 四个域名应得 172.18.x，`curl` 全部 200，耗时 30~150ms
- 回滚：`uci del_list dhcp.@dnsmasq[0].rebind_domain='hnsyu.edu.cn'; uci commit dhcp; /etc/init.d/dnsmasq restart`，删掉热插拔脚本，`ip route del` 三条路由
- **学校新增网段时要往脚本里加一行**（authserver 就在 172.18.18.0/24，与 10-28 处理 jwgl 时的网段不同）
- 千万不要用 `172.18.0.0/16` 或更大网段去顶 Docker，只加 /24；Docker 的 /16 仍然占着，具体 /24 优先
- 应急方案：内网路由又坏时，可临时把官网指到公网出口 `uci add_list dhcp.@dnsmasq[0].address='/www.hnsyu.edu.cn/220.170.193.14'`（学校换公网 IP 时要同步改）
- dnsmasq 重启时会打 `udhcpc: no lease, failing`，是重启瞬间旧实例的残留输出，WAN 租约不受影响（已复核 eth0 地址、默认路由与外网连通）
- 8 个 LAN 客户端都不需要改配置，重启 dnsmasq 后自动生效，浏览器 Ctrl+F5 即可
